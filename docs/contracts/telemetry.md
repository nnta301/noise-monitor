# Telemetry Contract v1

This document defines the shared data contract for telemetry ingestion, ensuring alignment across firmware, the simulator, the API, and the dashboard.

## Identity and Time

- `schema_version`: Must be `v1`.
- `device_id`: A stable device identifier (e.g., MAC address).
- `boot_id`: A unique UUID generated by the device upon each boot instance.
- `sequence`: A strictly increasing integer representing the packet sequence number within the current `boot_id`.
- `measured_at`: The measurement-batch start time. For synchronized devices, this must be a valid ISO 8601 timestamp (either UTC ending in `Z` or with a valid numeric offset). For devices with `time_sync_status` set to `monotonic`, this can be a truthful monotonic representation (e.g., milliseconds since boot).
- `timezone`: The local time zone of the device in IANA format (e.g., `Asia/Ho_Chi_Minh`).
- `time_sync_status`: Indicates the reliability of the device's clock. Valid values are `synced` (NTP successful), `unsynced`, or `monotonic` (device has no real-time clock access). Receipt order does not replace measurement order; unsynchronized packets must not silently use the server's receipt time as the measurement time.

## Batch Contents

Each packet represents a planned 10-second window. The payload contains arrays of exactly 10 entries each, corresponding to one second per entry.

- `median_p2p`: Array of 10 integers representing the median Peak-to-Peak (P2P) amplitude in relative ADC units (not dB SPL).
- `peak_p2p`: Array of 10 integers representing the absolute highest Peak-to-Peak amplitude in relative ADC units for that second.
- `quality_flags`: Array of 10 strings categorizing the sample quality. Valid values include `"ok"`, `"clipping"` (saturated samples), `"out_of_range"`, or `"missing"`.

**Handling Missing Data:**
Missing samples must be explicitly represented in the `quality_flags` array as `"missing"`. The corresponding value in the `median_p2p` and `peak_p2p` arrays must be `null`. Missing samples must never be replaced with `0`.

{

(Note: The example above is synthetic mock data, not a real measurement.)

## API Contract & Retry Behavior

**Endpoint:** `POST /api/v1/telemetry`

- **Idempotency & Deduplication:** The unique identifier for a packet is the composite key `(device_id, boot_id, sequence)`.
- **Retries:** The server must process retransmissions idempotently and record/display data gaps. If the server receives a packet with an existing key and identical content, it must return `202 Accepted` but create no additional database record.
- **Conflicts:** If the server receives a packet with an existing key but conflicting content, it must explicitly reject it with a `409 Conflict` error.
- **Validation:** Payloads that do not contain exactly 10 entries in the data arrays, omit required fields, or violate data types must be rejected with a `400 Bad Request`.
